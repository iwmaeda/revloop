> （英語）です。手順を 2 言語で持つと必ずずれが生じ、このファイルの場合ずれは安全性の欠陥になります。

## revloop とは

変更を **ブランチ作成 → 検証 → 分割コミット → push → PR 作成 → AI レビュアー起動 → 指摘の判定と修正 →
収束 → マージ** まで一本で回すコマンドです。Claude Code と Codex の両方で動き、ブランチを push
できる GitHub リポジトリと、コメントに応答する任意のレビュアー bot に対応します。対応していない
ものは「対応していないこと」に列挙してあります。

**変更の中身は作りません。** 出来上がった変更をレビュアーの前に置き、返ってきた会話を最後まで
運ぶ層だけを担います。

## 導入

```console
/plugin marketplace add iwmaeda/revloop
/plugin install revloop@revloop
```

コマンドは `/revloop:review-loop` です。プラグインが提供するコマンドは必ず `/<plugin>:<command>`
の形に名前空間化されるため、素の `/revloop` は存在しません。

続けて [`../permissions.md`](../permissions.md) の allowlist を設定してください。revloop が要求する
権限は、この種のワークフローを手書きしたときより **狭く** なっています:

```json
{
  "permissions": {
    "allow": [
      "Bash(gh api repos/{owner}/{repo}/:*)",
      "Bash(gh api -X POST repos/{owner}/{repo}/:*)",
      "Bash(gh api -X PUT repos/{owner}/{repo}/:*)",
      "Bash(gh api --paginate repos/{owner}/{repo}/:*)",
      "Bash(gh api graphql:*)",
      "Bash(gh pr:*)",
      "Bash(gh repo view:*)",
      "Bash(git:*)"
    ]
  }
}
```

`gh api` が `{owner}` / `{repo}` プレースホルダを展開するので、**このルールは今いるリポジトリ以外に
手が届きません**。

## 設定

設定ファイルは不要です。無ければベースブランチ・検証コマンド・ブランチ接頭辞・コミット規約を
リポジトリ自身から検出し、**実行前に** `source` 列（`flag` / `config` / `detected` / `builtin`）付きの
表を出します。この列を読めば、コードを読まずに「これは検出値だ」と分かります。

固定したいとき、あるいは独自のレビュアーを足したいときは `.revloop.json` を書きます
（[リファレンス](../configuration.md)・[例](../../examples/)）。
コメントに応答し、最初の返信が本番のレビューであるレビュアーなら、**追加に手順書やフェンスの変更は
要りません。** 本番の前に前置きコメントを出すレビュアーだけが例外です。

## 対応していないこと

どれも「気づかないうちに壊れる」ではなく、**理由を名前で言って止まる**設計です。

| 制限                                                   | 理由                                                                                                                            |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **fork では動きません**                                | `{owner}` が fork 側を指すのに PR は upstream にあるため。step 1 で abort します                                                |
| **同一リポジトリの topic branch のみ**                 | 1 ブランチにつき open PR 1 本。detached HEAD は推測せず abort します                                                            |
| **マージは merge commit のみ**                         | マージ用フェンスは引数を取らない（＝コマンド文字列が変わらない）ため。squash / rebase 不可                                      |
| **`copilot` は動かせません**                           | コメントによるトリガーを持たず、reviewer-request 経路は未実装です                                                               |
| **前置きコメントを出すレビュアーはフェンス変更が必要** | 非終端コメントの除外リストはフェンスの中にあり、設定はフェンスに届かないため。フェンス変更は全ユーザーの再承認 1 回にあたります |

詳細は英語版 README の [Limitations](../../README.md#limitations) を見てください。

## 設計の要点

- **嘘をつかない待機ループ。** 取得に失敗した出力は空で、空文字は `pending` も `fail` も含まないので、
  素朴な否定形の判定はすべて失敗を成功に化けさせます。緑はデータの肯定的な形からのみ判定します。
- **忘れても迂回できないマージゲート。** シェルの状態はツール呼び出しをまたいで残らないので、
  マージ段は自分で CI を再検査し、検査した sha を pin します。409 は読み戻して失敗として報告し、
  決してマージ済みとは言いません。
- **緩めずにレビュアー非依存にしたトリガー。** revloop は自分のトリガーに機械マーカーを付け、
  待機ループはレビュアー名ではなく自分が書いた文字列を照合します。`@誰か review this before merging`
  のような自然な人間のコメントが基準時刻を動かすことはなく、独自レビュアーにも
  プリセットと同じ厳密さが付きます。
- **一定に保たれる権限面。** 待機スクリプトは引数を取らず、リポジトリと PR を自分で解決するので、
  コマンド文字列が変わりません。「常に許可」が 1 度で永久に効きます。

理由は [`../design-notes.md`](../design-notes.md) に、各不変条件はそれを生んだ失敗と並べて
手順書の `## Notes` に書いてあります。
